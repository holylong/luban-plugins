# 代码审阅

## 什么时候用

- 用户让"看看这段改动有没有问题"、审 PR、审 diff
- 自己刚写完一段关键逻辑,提交前想先自审

## 读的顺序

1. **先读调用方**,再看被改的函数：不知道谁在用,就看不出签名变化的影响面。
2. **找行为变化**:同一个输入,新旧代码结果是否不同?只改格式/重命名的,直接跳过。
3. 按下面五项过一遍,**每项都要能说出触发条件**,说不出的不报。

## 五项检查

| 检查 | 要找的东西 |
| --- | --- |
| 正确性 | 边界值(空、0、1、最大)、off-by-one、取整与除零、字符串比较大小写 |
| 错误处理 | 失败分支是否吞掉异常、`catch` 里只打印不返回、资源在失败路径是否释放 |
| 并发 | 共享状态是否加锁/原子、是否假设单线程、异步里读旧闭包变量、await 前读的文件是否已过期 |
| 资源与性能 | 循环里发请求/查库、未限制的并发、未关闭的句柄、每次调用重建大对象 |
| 可测试性 | 是否把 I/O 写死在逻辑里、时间/随机数是否可控、是否有可断言的返回值而非只写日志 |

## 输出格式

按严重度分组,**每组最多三条**,每条给出:

1. 位置:`path:line`
2. 触发条件:什么输入/时序会出问题
3. 后果:数据错、崩溃、变慢、还是只是不好维护
4. 建议:具体到可执行的改法(必要时给代码)

```
[必须修] src/cache.ts:42 —— 并发写同一 key 时后写覆盖先写,缓存与磁盘不一致
触发:两个请求同时 miss 同一个 key
建议:用 per-key promise 去重,或写前比较版本号
```

## 不要做

- 不要只报风格问题(缩进、引号、命名偏好)占满输出
- 不要报"可能有问题"却给不出触发条件
- 不要建议为了抽象而抽象;能少改就少改
- 不要把"我看不懂"当成 bug

## 自检

- [ ] 每条都能复现或给出明确触发条件
- [ ] 严重度和影响面匹配(会不会丢数据 > 好不好读)
- [ ] 建议是可执行的,不是"考虑一下"
- [ ] 没有编造行号:引用前确认过
