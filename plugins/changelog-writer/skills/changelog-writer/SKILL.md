# 更新日志撰写

## 什么时候用

- 准备发版,需要写 `CHANGELOG.md` 一节或 GitHub Release 说明
- 用户问“这个版本改了什么”

## 收集素材

```bash
git log --oneline --no-merges $(git describe --tags --abbrev=0)..HEAD
git diff --stat $(git describe --tags --abbrev=0)..HEAD
```

看提交信息抓动机,看 diff 抓真实影响范围。两者不一致时以 diff 为准,并在日志里写实际行为变化。

## 写作规则

1. **按用户能否感知分组**,不按文件分组:

   - 新增 / 改进 / 修复 / 破坏性变更
2. 每条以动词开头,说清“现在能做什么”,不写“优化了代码”。

   - 反例:`重构了插件模块`
   - 正例:`插件面板支持搜索,输入即过滤`
3. 每条一行,必要时补一句限制条件(平台、开关、默认值)。
4. **同一轮工作里的小修、重构、测试整理合并成一条**,不逐条列。
5. 破坏性变更放最前面,写清迁移动作。
6. 版本号按项目的规则递增,不要自己发明格式。

## 模板

```markdown
## 2.9.5

### 新增

- 桌面端新增插件面板:搜索技能包目录、一键安装/卸载
- 安装前校验文件 sha256,校验失败不落盘

### 改进

- 插件目录缓存 5 分钟,搜索不再重复拉取

### 修复

- 修好安装后技能目录残留旧文件的问题
```

## 自检

- [ ] 每条都能被用户看见或摸到
- [ ] 没有把“重构”“调整代码结构”当成变化
- [ ] 破坏性变更写了迁移方法
- [ ] 版本号符合项目规则
