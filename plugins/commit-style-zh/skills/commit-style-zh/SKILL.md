# 中文提交信息

## 什么时候用

- 需要 `git commit`、`git commit --amend`，或帮用户改写提交信息时
- 生成 PR 标题、合并提交说明时

## 规则

1. **标题一行，不超过 50 个字符**，句尾不加句号。
2. 标题用 Conventional Commits 前缀，后跟中文描述：

   | 前缀 | 用途 | 例子 |
   | --- | --- | --- |
   | `feat` | 新增能力 | `feat: 桌面端支持插件搜索` |
   | `fix` | 修 bug | `fix: 修好手机端折叠后不滚动` |
   | `refactor` | 不改行为的重构 | `refactor: 抽出 pane 拖拽逻辑` |
   | `perf` | 性能 | `perf: 缓存 5 分钟降低插件目录请求` |
   | `docs` | 文档 | `docs: 补插件安装说明` |
   | `test` | 测试 | `test: 覆盖 sha256 校验失败` |
   | `chore` | 杂务 | `chore: 升版本到 2.9.5` |

3. **正文说为什么，不复述 diff**。每行不超过 72 字符，用 `-` 列要点，2–4 条足够。
4. 破坏性变更在正文里写 `BREAKING CHANGE:` 并说明迁移方式。
5. 一个提交只做一件事：顺手改的格式化、重命名单独提交。

## 反例与正例

反例：

```
update code
修复了一些问题
```

正例：

```
feat: 插件面板支持搜索与卸载

- 搜索在服务端过滤,目录只请求一次
- 卸载只删记录里的技能目录,不碰手写技能
- 安装前校验 sha256,校验失败不留文件
```

## 自检

- [ ] 标题有前缀、是中文、50 字以内
- [ ] 正文解释了动机而不是重复改动
- [ ] 没有把两件不相关的事塞进同一个提交
- [ ] 破坏性变更标了 `BREAKING CHANGE:`
